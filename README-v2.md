# ALPA v2 — 界面重制版 / UI Rebuild

> 原版 ALPA（Amazing Latency Performance Audit，作者 amazingb01 / Adiru）的延迟检测能力很强，
> 但整套 UI 是深色单色系，刻度、表格线、正文挤在一起，长时间盯着看很累。
> 这一版把界面层整个换掉，保留原有的 ETW / 性能计数器采集逻辑，并修掉了几处会误导结论的引擎缺陷。

---

## 0. 只想用，不想折腾 —— 下载这一个文件就够了

**下载 `ALPA_v2.exe`**（本仓库根目录里，约 6 MB 那个）。

- **就这一个文件**，不用下别的，也不用管任何 DLL。双击就能跑。
- ⚠️ 根目录里还有一个 `ALPA.exe`，那是**原作者的老版本**（深色界面、而且必须把旁边的
  6 个 DLL 和 `amd64\` 目录一起下载才能运行）。别下错，认准名字里带 **`_v2`** 的。
- 程序会自己弹一次 UAC 请求管理员权限：**同意**才有 DPC / ISR 内核追踪数据；
  **拒绝也能正常打开**，只是延迟相关页面是空的，其余页面（进程、体检、启动项、日志）都照常用。
- 想放到哪都行：桌面、U 盘、任意目录，不需要安装、不写注册表；
  只会在 `%LOCALAPPDATA%\ALPA_v2\` 下解包一份原生依赖（约 2.8 MB，见第 1 节）。
- **看不到 DPC / ISR 数据时先看第 1 节** —— 程序会把原因直接挂在界面上方，不用猜。

界面截图见 `screenshots/` 目录。

## 1. 「DPC / ISR 页面没数据」怎么排查

**先看程序自己怎么说。** 从 2.0.1 起，界面上方会直接挂出结论，不用去翻日志：

| 提示条 | 含义 | 怎么办 |
|---|---|---|
| 黄色「当前以普通权限运行…」+ 按钮「以管理员身份重启」 | 没提权，内核会话根本没尝试启动 | 点那个按钮，同意 UAC |
| 红色「内核 DPC / ISR 追踪没能启动 —— 这就是延迟数据空白的原因」 | 提权了，但会话创建失败，**原因就写在提示条上** | 点「查看日志」跳日志页（有完整堆栈）；若是别的监控工具占着会话，关掉后点「重试追踪」 |
| 没有提示条 | 追踪正常运行 | — |

日志位置：exe 同目录的 `ALPA_v2_Log_*.txt`。里面这几行的先后能直接定位问题：

```
trace library ready: ... (embedded)          ← 托管依赖 OK
native preflight ok: C:\...\ALPA_v2\runtime\2.0.1  ← 原生依赖 OK
native payload staged: ...                   ← 原生 DLL 已落盘
ALPA v2 engine LIVE - kernel DPC/ISR tracing active   ← 成功
```

### 关于「路径中具有非法字符」

这是**单文件打包引入过的一个坑**，已在 2.0.1 修掉，记录在此备查：

内核会话需要原生 `KernelTraceControl.dll`，它由 `OSExtensions.dll` 里的
`ETWKernelControl.LoadKernelTraceControl()` 加载，而 `TraceEvent.dll` 会从
**程序集所在目录**推出 `amd64\` 子目录。单文件版把 OSExtensions 从内存字节数组加载时，
`Assembly.Location` 是空字符串 —— 拼不出合法路径，于是抛 `路径中具有非法字符。`。

修法（`ui-v2/Embedded.cs`）：
- `OSExtensions.dll` **和整个原生 `amd64\` 目录**都作为资源嵌入 exe；
- 首次需要时解包到 `%LOCALAPPDATA%\ALPA_v2\runtime\<版本>\`（含 `amd64\` 子目录）；
- `OSExtensions` 用 `Assembly.LoadFrom` 从该目录加载，保证 `Assembly.Location` 有效；
- 同时 `SetDllDirectory(...\amd64)`，兜住「只给文件名直接 LoadLibrary」的写法。

所以程序首次运行会在 `%LOCALAPPDATA%\ALPA_v2\` 下写出约 2.8 MB 的原生文件（之后启动只校验、不重写）。
删掉也没关系，下次启动会重新解包；目录名带版本号，升级后不会误用旧文件。

## 2. 重新构建

有 .NET SDK：

```
dotnet build ui-v2\ALPA.V2.csproj -c Release
```

产物在 `ui-v2\build\ALPA_v2.exe`，复制到根目录即可。

只有 .NET Framework（没装 SDK）：

```
build-v2.bat
```

用系统自带的 `csc.exe` 编译并直接输出到根目录。代码刻意只用了 C# 5 语法，
所以老编译器也能过。

原理：4 个依赖 DLL 以**嵌入资源**打进 exe，由 `ui-v2/Embedded.cs` 里的 `Boot`
在运行时按需解出并 `Assembly.Load` —— 这就是「单文件」的实现方式，没有用任何第三方打包工具。

## 3. 顺手修掉的引擎问题

这些不是界面问题，是会让人得出错误结论的问题：

1. **ETW 会话释放不掉**
   原版退出时按 `"ALPKernelSession"` 找会话，实际会话名是 `"NT Kernel Logger"`，
   所以内核会话一直挂在系统里。v2 用正确的名字 `Stop()`。

2. **驱动名解析是 O(n) 线性扫描**
   原版每来一个 DPC 事件，都在几百个内核模块里线性查一遍符号。
   改成排序基址数组 + 二分查找 + 结果缓存。

3. **进程枚举卡 UI**
   原版在 UI 线程里 `Process.GetProcesses()`，每秒卡一下。
   挪到后台线程，并把周期放宽到 2 秒。

4. **性能计数器每秒重建**
   网络、磁盘计数器原版每秒 `new` 一次，v2 只建一次。

5. **提权后工作目录跑到 system32**
   原版用相对路径写日志和 CSV，提权后文件落到 `C:\Windows\System32`。
   v2 启动时把工作目录显式设成 exe 所在目录。

6. **显存计量读错计数器（本机实测）**
   `GPU Process Memory\Dedicated Usage` 在本机驱动上会返回离谱值：
   dandanplay 报 `4,616,381,632,512` 字节（≈4.2 TB），同一时刻
   `Local Usage` 只报 1.07 GB。这是 WDDM 计数器自身的怪癖，不是读数写错。
   v2 改用 `Local Usage` 优先，并对 >256 GB 的读数做兜底丢弃 ——
   否则「按显存排序」和 Score 列会被一个假数据整体带歪
   （修之前该进程 Score 显示 440667，修之后回到 390945 这个量级）。

7. **「追踪库是否存在」用 `File.Exists` 判断**
   单文件版把 DLL 打包进 exe 之后磁盘上根本没有那个文件，这个判断会误报缺失、
   把内核追踪整个关掉。改成真正 `Assembly.Load` 一次，顺便把版本号写进日志。

## 4. 导出的三样东西

| 文件 | 在哪 | 内容 |
|---|---|---|
| `ALPA_v2_Report_*.txt` | DPC 页「导出报告」 | **一次拿全的结论报告**：自动结论、系统信息、DPC/ISR 统计与分档计数、每核心数据、尖峰周期判定（含每一阵的起始时间）、驱动排行、健康检查建议。可以直接当参考结论存档或发给别人。 |
| `ALPA_v2_Spikes_*.csv` | DPC 页「导出」 | 超过阈值的尖峰明细：`序号,时间,自开始(秒),距上次(毫秒),驱动,位置,类型,时长(微秒)`。**位置 = 模块+偏移**（如 `ntoskrnl.exe+0x1a2b40`），是同一 Windows 版本上定位具体例程的指纹。 |
| `ALPA_v2_Drivers_*.csv` | 顶栏「导出」 | 每个驱动的次数与 P50/P95/P99/Max 全量。 |

### 4.1 尖峰 CSV 每一列是什么意思

导出尖峰时会**同时生成一份 `*_列说明.txt`**，忘了列含义直接看它。列定义：

| 列 | 含义 |
|---|---|
| `Seq` | 序号，本次导出内从 1 递增 |
| `Time` | 事件发生时刻，**ISO 8601 带 T**：`2026-09-28T11:07:37.020`。见下面的「为什么用 T 分隔」 |
| `Date` | 日期（`2026-09-28`）。Excel 识别为原生日期，可排序/筛选/透视 |
| `TimeHMS` | 时分秒（`11:07:37`）。Excel 原生时间，**秒可见** |
| `T+(s)` | 自本次程序启动（或上次清零）以来的秒数，单调递增，适合做间隔/分布分析 |
| `SincePrev(ms)` | 与**上一条**尖峰的间隔（毫秒）。想看「是不是固定间隔」就看这一列 |
| `Driver` | 驱动模块名——程序里「驱动延迟表」按这一列分组 |
| `Location` | 驱动 + 模块内偏移（如 `ntoskrnl.exe+0x80a33a`），定位具体内核例程的指纹 |
| `Type` | `DPC` 或 `ISR` |
| `Duration(us)` | 这一次事件本身的执行时间（微秒） |

### 4.2 为什么时间列是 `2026-09-28T11:07:37.020` 而不是带空格的写法

这是实测结论，不是审美选择。用 Excel COM 自动化逐格式验证过（同一时刻 `11:07:37.020`）：

| 写入 CSV 的格式 | Excel 实际显示 | 结果 |
|---|---|---|
| `2026-09-28 11:07:37.020` | **`07:37.0`** | ✗ 被当成「时间值」按 `mm:ss.0` 显示，**日期和小时全丢** |
| `2026-09-28 11:07:37` | `yyyy/m/d h:mm` | ✗ 秒仍看不到 |
| **`2026-09-28T11:07:37.020`** | **原样显示** | ✅ 识别为文本，零丢失 |
| `Date` + `TimeHMS` 两列 | `2026/9/28` + `11:07:37` | ✅ 原生类型，秒可见 |

所以导出同时给两种口径：`Time`（ISO，忠实可读、文本排序即时间排序）和 `Date`+`TimeHMS`（原生类型，方便做透视/图表）。
**若某列显示成 `#######`，那是列太窄**：`Ctrl+A` 全选后双击任意列边界让 Excel 自动适应列宽即可。

### 4.3 导出是「完整归档」，不含截断

| | 保留量 | 用途 |
|---|---|---|
| **导出 CSV / 报告** | **本次统计周期内的全部尖峰**（自启动或上次清零起，上限 20 万条） | 拿去做分析 |
| 界面尖峰日志 | 只显示**最近 4000 条**（可滚动） | 看实时情况 |

即：界面显示多少不影响导出。若真到了 20 万条上限，导出文件与报告里会**如实写明有多少条未保留**，不会假装完整。

### 4.4 为什么「驱动延迟表的最大」和「尖峰日志里的最大」不一样

这是两个不同口径，不是矛盾：

| | 覆盖范围 | 会不会忘掉旧事件 |
|---|---|---|
| **驱动延迟表 / 报告 / 指标卡** 的「最大」 | **整个会话**累计 | 不会。一旦出现 8.76 ms，就一直是 8.76 ms |
| **尖峰日志 / 尖峰 CSV** | 只保留**最近 N 条**（当前上限 4000 条） | **会**。一天的长测里，600~4000 条可能只够覆盖最近一两小时 |

所以完全可能出现「表里最大 8761 µs，而尖峰日志里最大只有 1175 µs」——
那一次 8761 µs 早于窗口起点，已经被滚动挤出去了。

为此有两个保障：
- DPC 页「尖峰日志」卡片副标题会直接写明：`全会话最长 X µs（驱动）· 本列表仅最近 N 条`；
- **报告新增《全会话最长的尖峰》一节**，按执行时间降序列出最坏的事件（含时刻、驱动、位置），
  **不受滚动影响** —— 想看「最坏那次是什么、什么时候、哪个例程」就看这里。

界面上的滚动：尖峰日志、驱动延迟表、进程表、启动项表都支持滚轮与滚动条
（滚轮消息只发给有焦点的控件，所以页面层做了转发，鼠标悬停在哪个列表上就滚哪个）。

## 5. 已知限制

- **DPC / ISR 数据需要管理员权限**：非管理员运行时不采集，概览页曲线会是空的，这符合预期。
- **`Processor Queue Length` 偏高不一定是异常**：这台机器实测过 68~74，
  用 PowerShell 直接读同一个计数器也是一样的值，属于系统真实负载，不是工具的 bug。
- **表格在极窄窗口下会出现横向滚动条**：这是有意为之 —— 列宽按内容自动量出来，
  放不下就横向滚，而不是把 PID / 内存这类关键数字截成 `4402…`。
- 启动时的界面缩放会写进日志（`ui scale ... (dpi ... x fit ...)`），
  界面大小或文字有异常时先看这一行。
- 首次运行会在 `%LOCALAPPDATA%\ALPA_v2\` 写一份原生依赖（约 2.8 MB）。不想留痕的话，
  把整个 `ALPA_v2` 目录删掉即可，程序下次启动会重新解包。
